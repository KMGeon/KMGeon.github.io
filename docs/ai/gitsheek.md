# 서론

---

최근 개발을 하면서 AI 도구를 단순히 코드 생성용으로만 쓰는 것보다, 내가 작성한 코드나 프로젝트 구조를 다시 점검하는 용도로 쓰는 일이 많아졌습니다.

처음에는 필요한 코드 조각을 물어보거나, 에러 메시지를 붙여 넣고 원인을 찾는 정도로 사용했습니다.
그런데 프로젝트 규모가 조금씩 커지면 단일 파일의 문제보다 **전체 구조가 어떻게 연결되어 있는지**, **어떤 부분이 유지보수에 부담이 되는지**, **README나 문서가 현재 코드와 맞는지** 같은 부분이 더 중요해집니다.

이번 글에서는 Gitsheek를 사용하면서 느낀 점을 정리해보려고 합니다.
정확히 말하면 특정 도구의 기능 소개라기보다는, AI 기반 코드 분석 도구를 사용할 때 어떤 관점으로 보면 좋은지에 대한 개인적인 기록에 가깝습니다.

제가 기대했던 부분은 크게 세 가지였습니다.

- **프로젝트 구조 파악**: 처음 보는 저장소를 빠르게 이해할 수 있는가?
- **개선 포인트 확인**: 코드 품질, 문서, 의존성 측면에서 놓친 부분을 찾을 수 있는가?
- **실제 개발에 도움 되는가**: 결과가 단순한 요약을 넘어서 다음 행동으로 이어질 수 있는가?

# 본론

---

## AI 코드 분석 도구를 사용하게 된 이유

개발을 하다 보면 내가 직접 만든 프로젝트임에도 시간이 지나면 구조가 흐릿해질 때가 있습니다.

처음에는 간단한 기능 하나로 시작했는데, 요구사항이 늘어나면서 서비스가 추가되고, 예외 처리가 붙고, 테스트 코드가 생깁니다.
그 과정에서 파일은 늘어나고 의존 관계도 조금씩 복잡해집니다.

문제는 이런 변화가 한 번에 크게 보이지 않는다는 점입니다.

예를 들어 다음과 같은 상황이 생깁니다.

| 상황 | 문제 |
| --- | --- |
| 기능 추가가 반복됨 | 비슷한 책임을 가진 코드가 여러 곳에 흩어짐 |
| README를 나중에 수정하지 않음 | 실제 실행 방법과 문서가 달라짐 |
| 의존성을 급하게 추가함 | 사용하지 않는 라이브러리가 남거나 버전 관리가 흐려짐 |
| 테스트를 필요한 부분만 작성함 | 중요한 흐름이 테스트 밖에 남음 |

혼자 개발할 때는 이런 부분을 매번 꼼꼼히 리뷰하기가 쉽지 않습니다.
그래서 AI가 저장소를 한 번 훑고, 내가 놓친 부분을 알려줄 수 있다면 꽤 유용할 것 같았습니다.

## Gitsheek에서 보고 싶었던 것

제가 Gitsheek 같은 도구에서 가장 먼저 보고 싶었던 것은 화려한 점수나 대시보드가 아니었습니다.

실제로 궁금했던 것은 아래에 가까웠습니다.

1. 이 프로젝트가 어떤 구조로 되어 있는지 설명할 수 있는가?
2. 핵심 진입점과 주요 모듈을 구분할 수 있는가?
3. README와 실제 코드 사이에 어긋난 부분을 찾을 수 있는가?
4. 개선이 필요한 부분을 너무 추상적이지 않게 말해줄 수 있는가?

AI 도구를 사용하다 보면 “코드 품질을 개선하세요”, “테스트를 추가하세요” 같은 말은 쉽게 나옵니다.
하지만 이런 답변은 실제로 큰 도움이 되지 않습니다.

개발자 입장에서 필요한 것은 조금 더 구체적인 피드백입니다.

예를 들면 이런 식입니다.

- 어떤 파일에서 책임이 과하게 몰려 있는지
- 어떤 기능 흐름에 테스트가 부족한지
- 문서에 적힌 실행 방법이 현재 설정과 맞는지
- 의존성 중 실제로 사용되지 않는 것이 있는지
- 에러 처리나 예외 메시지가 사용자 입장에서 충분한지

결국 중요한 것은 AI가 “좋다/나쁘다”를 판단하는 것이 아니라, 내가 다음에 무엇을 확인해야 하는지 정리해주는 것입니다.

## 저장소를 분석할 때 유용했던 관점

AI 기반 저장소 분석 도구를 사용할 때는 결과를 그대로 받아들이기보다, 몇 가지 기준을 두고 보는 것이 좋다고 느꼈습니다.

### 1. 구조 요약은 빠른 온보딩에 도움이 된다

처음 보는 저장소를 이해할 때 가장 시간이 걸리는 부분은 “어디서부터 봐야 하는가”입니다.

파일 목록만 봐서는 어떤 모듈이 핵심인지 바로 알기 어렵습니다.
특히 프론트엔드와 백엔드가 같이 있거나, 설정 파일이 많은 프로젝트에서는 더 그렇습니다.

이때 AI가 프로젝트의 큰 구조를 먼저 요약해주면 출발점이 생깁니다.

예를 들어 아래와 같은 식의 요약이 있으면 코드를 읽는 순서를 정하기가 쉬워집니다.

```text
- 설정 파일은 루트에 모여 있다.
- 실제 화면 구성은 src/pages 또는 docs 하위에서 관리된다.
- 공통 스타일은 별도 디렉터리에서 관리된다.
- 배포 설정은 GitHub Pages 또는 CI 설정과 연결되어 있다.
```

물론 이 요약이 항상 정확한 것은 아닙니다.
그래도 처음부터 모든 파일을 열어보는 것보다, 어느 정도 방향을 잡고 들어갈 수 있다는 점에서 도움이 됩니다.

### 2. README 분석은 생각보다 중요하다

개인 프로젝트에서는 README를 처음에만 작성하고 방치하는 경우가 많습니다.
저도 프로젝트가 어느 정도 동작하기 시작하면 코드 수정에 집중하게 되고, 문서 정리는 뒤로 밀리는 편입니다.

그런데 README는 생각보다 중요합니다.

나중에 다시 프로젝트를 열었을 때 가장 먼저 보는 문서이기도 하고, 다른 사람이 프로젝트를 이해할 때도 진입점이 됩니다.

AI 분석 도구가 README를 기준으로 다음과 같은 부분을 짚어주면 꽤 실용적입니다.

| 확인 항목 | 예시 |
| --- | --- |
| 실행 방법 | 현재 package script나 Gradle task와 문서가 일치하는가 |
| 환경 변수 | 필요한 값이 문서에 빠져 있지 않은가 |
| 프로젝트 설명 | 실제 기능과 README 설명이 어긋나지 않는가 |
| 배포 방법 | 배포 환경이나 브랜치 전략이 설명되어 있는가 |

코드 자체가 아무리 잘 작성되어 있어도, 실행 방법이 문서화되어 있지 않으면 시간이 지나 다시 잡기 어렵습니다.
이런 부분을 자동으로 확인해주는 것은 생각보다 체감이 컸습니다.

### 3. 코드 품질 피드백은 맥락을 같이 봐야 한다

AI가 코드 품질을 분석할 때 자주 언급하는 부분은 중복, 복잡도, 책임 분리, 테스트 부족 같은 것들입니다.

이 자체는 맞는 말입니다.
다만 모든 지적을 바로 수정해야 하는 것은 아닙니다.

예를 들어 작은 개인 프로젝트에서 파일 하나가 조금 길다고 해서 무조건 분리하는 것이 좋은 선택은 아닐 수 있습니다.
오히려 너무 이른 추상화가 코드를 더 읽기 어렵게 만들기도 합니다.

그래서 저는 AI의 피드백을 볼 때 아래처럼 구분해서 보려고 했습니다.

| 구분 | 판단 기준 |
| --- | --- |
| 바로 수정할 것 | 버그 가능성이 있거나 실행에 영향을 주는 문제 |
| 나중에 정리할 것 | 구조 개선, 네이밍, 문서 보완 |
| 보류할 것 | 현재 규모에서는 과한 추상화가 될 수 있는 제안 |

AI의 장점은 넓게 훑어보는 것입니다.
반대로 실제 우선순위를 정하는 것은 여전히 개발자가 해야 합니다.

## 사용하면서 아쉬웠던 점

AI 도구를 사용할 때 가장 조심해야 하는 부분은 그럴듯한 설명입니다.

분석 결과가 자연스럽게 쓰여 있으면 맞는 말처럼 보이지만, 실제 코드를 확인해보면 일부는 추측에 가까울 때가 있습니다.

특히 아래와 같은 결과는 한 번 더 확인하는 것이 좋습니다.

- 실제로 존재하지 않는 파일이나 설정을 언급하는 경우
- 코드 흐름을 단순화해서 잘못 설명하는 경우
- 테스트가 있는데도 없다고 판단하는 경우
- 의존성 사용 여부를 정확히 구분하지 못하는 경우

그래서 AI 분석 결과는 최종 결론이라기보다 리뷰 초안에 가깝게 보는 편이 맞다고 생각합니다.

개발자가 직접 확인해야 할 목록을 뽑아주는 도구로 보면 유용하지만, 결과를 그대로 믿고 수정하면 오히려 잘못된 방향으로 갈 수 있습니다.

## 어떻게 활용하면 좋을까

개인적으로는 Gitsheek 같은 도구를 아래와 같은 상황에서 사용하면 좋다고 느꼈습니다.

### 1. 오래된 개인 프로젝트를 다시 볼 때

예전에 만든 프로젝트를 다시 열면 내가 작성한 코드인데도 낯설 때가 있습니다.
이때 전체 구조 요약을 먼저 받아보면 다시 맥락을 잡는 데 도움이 됩니다.

### 2. README를 정리하기 전에

README를 처음부터 다시 쓰려고 하면 막막합니다.
AI 분석 결과를 바탕으로 현재 프로젝트의 기능, 실행 방법, 기술 스택을 먼저 정리하면 문서 작성이 훨씬 수월합니다.

### 3. 리팩터링 전에

리팩터링은 바로 코드를 고치는 것보다, 먼저 어디가 문제인지 보는 과정이 중요합니다.
AI가 중복 코드, 책임이 큰 파일, 테스트가 부족한 흐름을 후보로 뽑아주면 우선순위를 정하기 좋습니다.

### 4. 다른 사람의 저장소를 빠르게 이해할 때

오픈소스나 예제 프로젝트를 볼 때도 도움이 됩니다.
모든 파일을 처음부터 읽기 전에 구조 요약을 보고 들어가면, 핵심 파일을 찾는 시간을 줄일 수 있습니다.

# 마무리

---

Gitsheek를 사용하면서 느낀 점은 AI 코드 분석 도구가 개발자를 대신해주는 도구라기보다는, 개발자가 더 빨리 판단할 수 있게 도와주는 도구에 가깝다는 것입니다.

코드를 직접 읽고, 실행해보고, 테스트하는 과정은 여전히 필요합니다.
하지만 그 전에 전체 구조를 파악하고, 놓친 부분을 체크하고, 개선 후보를 정리하는 데에는 충분히 의미가 있었습니다.

특히 개인 프로젝트나 사이드 프로젝트처럼 리뷰어가 따로 없는 환경에서는 이런 도구가 한 번쯤 제3자의 시선처럼 작동할 수 있습니다.

다만 AI가 말한 내용을 그대로 믿기보다는, 실제 코드와 문서를 기준으로 다시 확인하는 과정이 필요합니다.
결국 좋은 도구는 결론을 대신 내려주는 것이 아니라, 더 나은 질문을 하게 만들어주는 쪽에 가깝다고 생각합니다.
